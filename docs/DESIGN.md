# DESIGN.md — HWPX 양식 채움 전체 처리 흐름

이 문서는 HWPX 양식 기반 내용 채움 서비스의 전체 처리 흐름을 정리한다.
각 단계가 무엇을 받고 무엇을 넘기는지 짧게 기록한다.
구현 상태나 검증 통과를 뜻하지 않는다.

## 설계 방향

- A는 양식 원본(HWPX)으로, 표·문단·서식·고정 문구를 보존한다.
- B는 내용 원본(HWPX·TXT·Markdown·붙여넣기)으로, 근거 있는 내용만 입력란에 채운다.
- 예선의 “A 문장 제거” 규칙과 “B 구조 그대로 유지” 규칙은 적용하지 않는다.
- Solar는 내용 연결 제안만 맡는다.
- 실제 편집과 검증은 규칙 기반 엔진이 맡는다.
- 분석부터 생성, 보고서와 API까지의 공통 계약은 `docs/TEAM_CONTRACT.md`를 기준으로 본다.

## 처리 흐름 개요

1. 브라우저 제출
2. A 구조·분석 (hwpx/)
3. B 원문 추출 (hwpx/)
4. 규칙 연결 (hwpx/)
5. Solar 제안 (solar/)
6. 근거 검증 (hwpx/)
7. 사용자 검토 (web/)
8. 선택한 값 기입 (hwpx/)
9. 결과 검증 (hwpx/)
10. 다운로드 (api/)

## 1. 브라우저 제출

- 받는 것: A 양식 파일, B 내용(HWPX·TXT·Markdown·붙여넣기), B가 파일인지 붙여넣기인지 같은 출처 정보
- 넘기는 것: 서버로 보낼 최소 원본과 제출 메타데이터
- 이 단계는 아직 분석이나 채움을 하지 않는다.
- 브라우저는 A와 B를 보유한다.
- 요청마다 필요한 원본만 서버로 보낸다.
- 서버에 문서 세션을 저장하지 않는다.

## 2. A 구조·분석 (hwpx/analyze.py)

- 받는 것: A 파일, 원본 A의 해시
- 넘기는 것: 입력란 후보 목록, 구조 정보, 고정 문구, 편집 가능 구간 정보, 분석 메타데이터
- 이 단계는 “어디를 채울 수 있는지”를 찾는 단계다.
- 실제 채우기는 하지 않는다.

주요 내용:
- A의 모든 section을 문서 순서로 읽는다.
- namespace, 병합 범위, 중첩 표를 구분해 처리한다.
- 같은 텍스트가 부모 셀과 자식 셀에 함께 나타나면 두 번 세지 않는다.
- 빈 셀, 라벨 뒤 공백, 단위만 남은 칸, 자리표시자를 후보로 본다.
- 글이 여러 run에 나뉘어 있어도 문단 기준으로 분석한다.
- 직명·성명, 주소·우편번호, 시간·분은 별도 구간으로 나눠 본다.
- 표 제목과 구역, 다단 헤더, 연도, 좌우 영역, 단위 범위는 구분 정보로 유지한다.
- 안내문과 기존 기입값은 보호한다.
- 안전한 문단은 수동 보정 후보로 남긴다.
- 라벨과 입력 위치를 구분한다.
- 분석하지 못한 정보는 이유와 함께 남기고, 분석 상태를 결과 입력값으로 넣지 않는다.

공통 계약과의 관계:
- `docs/TEAM_CONTRACT.md`의 A 분석 계약과 필드 이름·데이터 흐름을 맞춘다.
- 화면 위치와 서버 내부 편집 위치는 구분한다.

## 3. B 원문 추출 (hwpx/source.py)

- 받는 것: B 원본(HWPX·TXT·Markdown·붙여넣기), 원본 B의 해시, 출처 정보
- 넘기는 것: 원문 블록 목록, 검색용 정리 텍스트, 추출 메타데이터, 누락/실패 정보
- B의 서식은 결과에 가져오지 않는다.
- 표 구조는 값의 의미를 판단하는 데만 사용한다.

주요 내용:
- 원문 텍스트와 순서를 보존한다.
- 제목, 문단, 목록, 표의 행과 열, 병합 관계를 문맥으로 기록한다.
- 각 원문 블록에 고유 ID와 위치를 붙인다.
- 검색용으로 정리한 텍스트는 원문과 따로 관리한다.
- 표 내용 연결과 단위 변환은 이 단계가 직접 책임지지 않는다.
- 추출하지 못한 내용은 누락으로 기록한다.

공통 계약과의 관계:
- `docs/TEAM_CONTRACT.md`의 B 추출 계약과 필드 이름·데이터 흐름을 맞춘다.
- 원문과 정규화 텍스트를 같은 필드로 섞지 않는다.

## 4. 규칙 연결 (hwpx/rules.py)

- 받는 것: A 입력 후보, B 근거(원문 블록, 정리 텍스트, 표 문맥)
- 넘기는 것: 규칙 기반으로 확정된 채워짐 후보(값·근거·적용 위치가 함께 붙은 결과)
- 명확성이 높은 것부터 처리한다.
- 애매한 항목은 뒤로 남긴다.

주요 내용:
- 라벨, 주변 문맥, 표 행·열 제목, 연도, 단위를 기준으로 먼저 연결한다.
- 표 연결은 위치나 열 개수만 기준으로 삼지 않는다.
- 상위 금액을 하위 행마다 복사하지 않고, 소계와 상세를 구분한다.
- 단위 변환은 Decimal로 정확히 처리한다.
- 여러 사실 조합으로 하나의 값을 만들 때는 모든 근거를 남기고 검토를 요구한다.
- 자료 없음, 충돌, 분석 실패는 서로 구분해 다룬다.

## 5. Solar 제안 (solar/client.py, solar/batches.py)

- 받는 것: 규칙으로 연결되지 않은 A의 남은 입력 후보, B 근거, 이 시점까지 쌓인 채움 정보
- 넘기는 것: Solar 제안 값, 제안 이유, 원문 블록 ID, 인용문, 검토 필요 여부와 이유
- Solar는 내용 연결 제안만 맡는다.
- XML 생성이나 바이트 수준 편집은 Solar에 맡기지 않는다.
- 모델의 신뢰도 표시만으로 확정하지 않는다.

주요 내용:
- `solar/batches.py`는 입력란 후보와 관련 원문을 배치로 나눈다.
- `solar/client.py`는 단일 요청과 응답을 검사한다.
- Solar 응답은 값, 필드 ID, 원문 블록 ID, 인용문, 검토 필요 여부와 이유를 담는다.
- 정상 내용 증가에 따른 페이지 이동과 보호 구조 손상을 구분한다.
- Solar가 제안한 값은 확정 값이 아니라 검토 대상이다.

## 6. 근거 검증 (hwpx/evidence.py)

- 받는 것: 규칙 기반 채움 결과, Solar 제안 값, 각 값의 근거
- 넘기는 것: 근거 검사 결과(어떤 값이 어떤 근거로 연결됐는지, 근거가 부족하거나 충돌하는지, 검토가 필요한 항목)
- 이 단계는 생성 전에 값이 어디서 왔는지 다시 보는 관문이다.

주요 내용:
- 근거가 충분한지, 충돌하는지, 검토가 필요한 항목을 가린다.
- 근거 없음, 충돌, 응답 누락, 분석 실패는 구분해서 표시한다.
- 실패한 항목 때문에 정상 제안을 버리지 않는다.

## 7. 사용자 검토 (web/)

- 받는 것: 표 셀과 입력란 목록, 각 항목의 라벨·값·근거·충돌 후보
- 넘기는 것: 사용자가 선택한 채움 항목, 적용/미적용 결정, 수동 수정 내역
- 화면이 편집 위치를 임의로 지정하지 않는다.
- 클라이언트나 화면이 새 좌표를 보내 편집 위치를 바꾸지 못하게 한다.

주요 내용:
- 각 항목에 라벨, 값, 근거, 충돌 후보를 함께 보여준다.
- 값만 나열하지 않고, 값이 어디서 왔는지와 충돌이 있는지도 함께 볼 수 있어야 한다.
- 사용자는 제안을 검토하거나 선택하거나 직접 수정할 수 있다.
- 수동 수정은 자동 제안과 구분해서 기록한다.
- 입력을 변경하면 이전 응답과 다운로드를 무효화한다.

## 8. 선택한 값 기입 (hwpx/generate.py, hwpx/corrections.py)

- 받는 것: A 원본, 선택 반영 목록, 근거 정보, A와 B의 해시
- 넘기는 것: A의 선택된 구간만 편집된 결과 문서, 편집 위치 결정, 저장 근거 정보
- 문단 전체 편집과 내부 입력란이 겹치면 거부한다.
- 실제 편집 위치는 서버 내부에 둔다.
- 화면에는 후보 ID와 구조 위치만 보여 준다.

주요 내용:
- 빈 자동 제안과 미선택은 A를 그대로 유지한다. 사용자가 명시적으로 선택한 수동 비우기는 허용한다.
- 수동 입력은 원문에서 확인된 값과 구분해 남긴다.
- 보정(`hwpx/corrections.py`)은 안전한 candidateId의 라벨과 활성화 여부만 보정한다.
- 값 수정은 사용자 편집 목록에서 처리한다.
- 긴 내용은 자르거나 글꼴을 줄이지 않고 넘침 경고만 남긴다.
- 고정 문구, 표와 병합, 스타일과 이미지는 보호한다.
- 생성 전에 원본 A의 해시와 입력란의 실제 위치, 편집 가능 범위를 다시 확인한다.
- 클라이언트가 보낸 위치나 편집 정보를 그대로 신뢰하지 않는다.

## 9. 결과 검증 (hwpx/validate.py)

- 받는 것: 편집된 결과 문서, A의 선택 구간과 채움 정보
- 넘기는 것: 검증 결과(변경 구간이 의도한 범위인지, A의 보존 항목이 유지됐는지, 문제가 있는지)
- 이 단계는 내려보내기 전 마지막 확인이다.

주요 내용:
- 결과 HWPX의 ZIP과 XML을 다시 읽는다.
- 선택한 값이 지정한 위치에 들어갔는지 확인한다.
- A의 표 행·열, 병합, 스타일 참조, 고정 문구, 이미지와 페이지 설정이 보존됐는지 검사한다.
- 수정하지 않은 부분의 변경도 확인한다.
- 자동 제안 값은 B의 근거와 대조하고, 수동 수정 값은 별도로 표시한다.
- 내용을 임의로 요약하거나 줄이지 않는다.
- 내용 길이 경고만으로 결과 생성을 막지 않는다.
- ZIP/XML 손상, 허용 범위 밖의 변경처럼 구조 검증에 실패하면 결과 파일을 제공하지 않는다.
- 실제 렌더링을 확인하지 않았다면 시각 검증 완료로 표시하지 않는다.

## 10. 다운로드 (api/service.py, api/index.py)

- 받는 것: 검증된 결과 문서, 근거·검토 정보, 요청한 범위
- 넘기는 것: 최종 HWPX 파일, 근거·검토 흐름이 드러나는 보고서
- 이 단계가 사용자가 받는 결과물이다.

주요 내용:
- `api/service.py`는 상태, 분석, 제안, 생성, 미리보기를 하나의 dispatch로 처리한다.
- `api/index.py`는 같은 dispatch를 배포 환경에서 노출한다.
- 보고서는 실제 채움 계약에 맞춰 작성한다.
- 기존 보고서 스키마가 이 기능을 표현하지 못하면 그대로 맞춰 넣지 않는다.
- 중간 JSON은 사용자에게 길게 보여 주지 않는다.

## 책임 구분

### hwpx/

- 문서 분석, B 원문 추출, 규칙 연결, 근거 검증, 보정, 생성, 검증을 맡는다.
- 대표 파일: `hwpx/analyze.py`, `hwpx/source.py`, `hwpx/rules.py`, `hwpx/evidence.py`, `hwpx/corrections.py`, `hwpx/generate.py`, `hwpx/validate.py`
- Solar가 XML을 만들거나 서식을 바꾸는 구조가 되지 않게 한다.

### solar/

- 내용 연결 제안만 맡는다.
- 대표 파일: `solar/client.py`, `solar/batches.py`
- XML 생성, 서식 적용, 실제 편집과 검증은 맡지 않는다.

### api/

- 요청 처리, dispatch, 서버 검증을 맡는다.
- 대표 파일: `api/service.py`, `api/index.py`, `scripts/dev_server.py`
- 서버 내부에서 해시와 편집 가능 범위를 다시 확인한다.

### web/

- 업로드, 검토, 다운로드를 맡는다.
- 대표 구성: `web`
- 브라우저가 A와 B를 보유하고, 요청마다 필요한 원본만 서버로 보낸다.
- 화면에 편집 위치를 임의로 지정하지 않는다.

## 데이터 흐름 요약

- 브라우저 제출 → api/ 진입
- A 분석: hwpx/analyze.py
- B 추출: hwpx/source.py
- 규칙 연결: hwpx/rules.py
- Solar 제안: solar/batches.py → solar/client.py
- 근거 검증: hwpx/evidence.py
- 사용자 검토: web/
- 선택 값 기입: hwpx/corrections.py → hwpx/generate.py
- 결과 검증: hwpx/validate.py
- 다운로드: api/service.py → api/index.py

## 충돌·유의 사항

- `docs/TEAM_CONTRACT.md`에 분석, 추출, 규칙 연결, Solar 제안, 근거 검증, 보정과 편집, 생성, 보고서와 미리보기, API 계약이 있다.
  - DESIGN.md는 이 계약의 필드 이름과 데이터 흐름을 따른다.
  - 해시, 위치 객체, 추출 상태, 실패와 누락 코드, 근거 필드 관계, 긴 블록 분할과 전송 제한은 공통 계약의 정의를 따른다.
- `references/08-output-contract.md`와 `examples/example-04-docx-fallback.md`에는
   HWPX를 못 만들 때 DOCX/PDF를 성공 결과로 대신 제공하는 방향의 표현이 남아 있다.
  - 이 방향은 루트 SKILL.md의 “HWPX를 목표로 하되 DOCX/PDF를 성공 결과로 대신 제공하지 않는다”와 충돌한다.
  - 해당 참고 자료의 폴백 규칙은 적용하지 않는다. 루트 SKILL.md의 절대 규칙을 따르며 검증된 HWPX만 성공 결과로 제공한다. 예선 원본은 보존한다.
- Solar가 XML을 만들거나 화면이 편집 위치를 임의로 지정하는 구조는 두지 않는다.
- 이 문서는 설계 정리이며, 구현 완료나 테스트 통과를 뜻하지 않는다.
